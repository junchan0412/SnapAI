# SnapAI 项目检查与清理报告

日期：2026-10-25（Asia/Shanghai）。检查基线：`main` / `6d36f6a54043332ff2ff4d5bb815c1df72eca827`；`Resources/Info.plist` 版本 **2.1.0**。开始检查时 Git 工作区干净。本报告及文档整理属于基线之后的未提交修改。

## 1. 当前判断

SnapAI 已具备清晰的产品主线：取词或截图 → 选择动作处理 → 阅读与追问 → 确认写回 → 从本机历史继续。2.1.0 已补齐旧报告中的独立双模型请求、Shortcuts 正文返回、图片三模式和持久会话等主要实现缺口。当前更适合进入可靠性与实机兼容性收尾，而不是继续横向堆叠功能。

工程目录的主要问题是**文档的层级与时间状态混杂**：旧评估、现行规范、发布记录和过程日志平铺，README 的多个历史补丁版本抢占入口，已失效的临时日志链接也仍像有效证据。代码模块本身已有边界检查和离线回归基础，本次未发现需要通过大规模源码搬迁解决的结构问题。

## 4. 当前能力与剩余缺口

| 领域 | 当前状态及后续关注点 |

| 双模型与自动化 | 源码中的每侧请求持有独立 client；Shortcuts 返回正文已有 runtime 证据；系统 Shortcuts 发现与下游串联仍需完整设备验收 |
| 会话 | 本机 SQLite 保存、恢复、分支及用户确认摘要压缩已实现；恢复不沿用旧文档写回目标，应继续保持这一边界 |
| 取词与写回 | 有源文、目标、选区和剪贴板保护；既有 TextEdit/Word 20 次尝试中 18 次达到相应预期，包含取词、实际写回及保护拒绝；不能作为四应用全面通过 |

## 5. 性能与可优化方向

既有 2026-10-25 固定设备的 30 样本基线：首次输入窗 P95 199.5 ms、首次结果窗 P95 203.3 ms；100k 混合 Markdown 解析 P95 18.92 ms；500 条历史完整搜索暖连接 P95 303.3 ms。窗口口径从 `controller.show` 到就绪，不含硬件快捷键、系统启动或网络；解析耗时不等于 UI 帧耗时，完整搜索也不等于连续输入后的显示时延。

优先优化方向：

1. **补齐用户实际链路的测量。** 记录快捷键到可输入、键入到结果可见、正文完成到 Markdown 就绪、上下滚动后阅读位置偏移；先建立同设备同配置重复基线，再决定数值门禁。
2. **收敛历史语义搜索成本。** 用唯一文本、不同查询和冷缓存样本测量，明确 FTS 先显示及取消是否及时；已有重复查询缓存基线不能代表全部历史。证据确定热点后再调整候选量或缓存策略。
3. **检验会话与图片的资源成本。** 完整 UI 下测试大图添加/裁剪/删除、恢复多轮带图会话、取消在途请求及 30 分钟空闲趋势；分别记录 footprint、RSS 与峰值。
4. **降低回归定位成本。** 当前 XCTest 把内部 case 聚合为一个测试；以后可按请求、隐私、存储、会话等现有边界拆成可单独定位的 test，避免同时重写测试框架。
5. **整理编译兼容性与文案。** 本轮构建出现 `TextCapture.swift:383` 的 AXUIElement 强转可选值 warning，以及 `ImageTextRecognitionTests.swift:89` 的异步上下文 semaphore wait warning；后者在 Swift 6 language mode 下会升级为错误。先消除 warning，再单独评估语言模式迁移。

产品上继续围绕取词、截图、阅读和可控写回完善。文件检索/RAG、泛用 Agent、应用自动配置与逐段接受属于另行验证需求的候选，本轮不进入已承诺功能，也不为其预建抽象层。
